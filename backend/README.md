# k- — backend

Бэкенд веб-приложения на **TypeScript + Express 5 + PostgreSQL**.

Что реализовано: регистрация и вход по JWT, профиль пользователя, избранное, история навигации,
объекты защиты, материалы, их исходные файлы, полнотекстовый поиск и калькулятор пошлин. Наполнение сайта (статьи,
чек-листы) хранится в папке [`../content`](../content/README.md) и при каждом развёртывании
синхронизируется в PostgreSQL; пользовательские данные живут только в базе.
Фронтенд живёт в этом же репозитории, в [`../frontend`](../frontend/README.md). Контракт API: [docs/api.md](../docs/api.md).

Все команды ниже выполняются из папки `backend/`.

## Требования

- **Node.js 24 LTS** или новее, npm (идёт вместе с Node.js)
- **PostgreSQL 13+** (используется встроенная `gen_random_uuid()`); локально и в CI — 17.
  Без БД сервер запускается, но эндпоинты с данными отвечают `503 DATABASE_UNAVAILABLE`.

## Быстрый старт

```bash
cd backend
npm install
cp .env.example .env    # заполнить DATABASE_URL и JWT_SECRET
npm run db:migrate      # создать таблицы
npm run db:seed         # загрузить наполнение из ../content
npm run db:seed:demo    # для разработки: демо-пользователь (нужен SEED_DEMO_PASSWORD)
npm run dev             # http://localhost:3001
```

## Конфигурация

Все настройки задаются переменными окружения. Локально их можно хранить в файле `backend/.env`:
он загружается через dotenv (из какой бы папки ни запускалось приложение) и **не попадает в Git**.
Переменные, уже заданные в окружении процесса, имеют приоритет над `.env`.

| Переменная                 | Обязательна | По умолчанию            | Описание |
| -------------------------- | ----------- | ----------------------- | -------- |
| `NODE_ENV`                 | нет         | `development`           | `development` / `production` / `test` |
| `PORT`                     | нет         | `3001`                  | Порт HTTP-сервера |
| `DATABASE_URL`             | **да**      | —                       | Подключение к PostgreSQL |
| `FRONTEND_ORIGIN`          | нет         | `http://localhost:3000` | Origin фронтенда для CORS, несколько — через запятую |
| `JWT_SECRET`               | **да**      | —                       | Секрет подписи access-токенов, не короче 32 символов (`openssl rand -base64 48`) |
| `ACCESS_TOKEN_TTL_SECONDS` | нет         | `900`                   | Срок жизни access-токена |
| `REFRESH_TOKEN_TTL_DAYS`   | нет         | `30`                    | Срок жизни refresh-токена |
| `CONTENT_DIR`              | нет         | `../content`            | Папка наполнения относительно `backend/` |
| `SEED_DEMO_PASSWORD`       | нет         | —                       | Только для `db:seed:demo`: пароль демо-пользователя `anna_kuznetsova` (от 8 символов) |

Подключение к БД задаётся **только** через `DATABASE_URL`:

```
postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

- Спецсимволы в пароле кодируются (`@` → `%40`, `:` → `%3A`, `/` → `%2F`).
- Для TLS добавьте параметр, например `?sslmode=require`.

При старте конфигурация проверяется. Если что-то задано неверно, приложение завершится с понятным
списком ошибок; значения секретов в сообщения не попадают.

**Смена `JWT_SECRET`** делает недействительными все выданные access-токены: пользователи получат
`INVALID_TOKEN` и должны будут обновить токен через refresh (refresh-токены от секрета не зависят).

## База данных

### Локальная база

Для разработки используется база `k_dev`, её владелец — роль `k_app`. Пошаговая инструкция для
Linux и Windows (установка PostgreSQL, создание базы, `.env`, запуск) — в
[корневом README](../README.md#локальный-запуск). Кратко для Debian/Ubuntu (нужен sudo):

```bash
# 1. PostgreSQL из репозитория дистрибутива (на Debian 13 это версия 17).
#    Служба запускается сама и слушает только localhost:5432.
sudo apt-get install -y postgresql

# 2. Роль и пустая база. Пароль придумайте сами (лучше из [A-Za-z0-9], чтобы не кодировать его в URL).
sudo -u postgres psql -v ON_ERROR_STOP=1 -v app_password='ВАШ_ПАРОЛЬ' < db/create-dev-db.sql

# 3. В backend/.env:
# DATABASE_URL=postgresql://k_app:ВАШ_ПАРОЛЬ@localhost:5432/k_dev

# 4. Таблицы и данные
npm run db:migrate
npm run db:seed
npm run db:seed:demo
```

Проверка: `npm run dev`, затем `curl http://localhost:3001/api/health` → `{"status":"ok","database":"up"}`.

Удалить базу: `sudo -u postgres psql -c 'DROP DATABASE k_dev' -c 'DROP ROLE k_app'`.

### Миграции

- Файлы `db/migrations/NNN_описание.sql` применяются по порядку имён командой `npm run db:migrate`.
- Каждый файл выполняется в отдельной транзакции и записывается в таблицу `schema_migrations`;
  применённые файлы повторно не выполняются. Параллельные запуски сериализуются advisory-lock.
- **Применённую миграцию не редактируют** — изменения схемы оформляются новым файлом
  (`002_....sql`). Откат не автоматизирован: при необходимости пишется обратная миграция.

Схема (`001_initial_schema.sql` — `003_fee_schedules.sql`):

| Таблица | Содержимое |
| --- | --- |
| `users` | Пользователи: логин, email (уникальны без учёта регистра), имя, хеш пароля, время согласия на обработку ПДн |
| `refresh_tokens` | SHA-256-хеши refresh-токенов, срок действия, время отзыва |
| `protection_objects` | Объекты защиты (код, базы данных, бренд…); `is_published` |
| `materials` | Статьи, чек-листы, памятки; содержимое — JSONB-блоки; файл DOCX; `is_published` |
| `material_relations` | Связанные материалы с порядком |
| `favorites` | Избранное пользователей |
| `history_entries` | История навигации пользователей |
| `fee_schedules` | Калькулятор пошлин: по строке на файл `content/fees/*.yaml` — параметры и пошлины в JSONB |

### Наполнение и сидеры

**`npm run db:seed`** синхронизирует базу с папкой `../content` (формат и правила —
[content/README.md](../content/README.md)). Запускается при каждом развёртывании и в CI:

- всё наполнение сначала проверяется: уникальность и формат `id`, существование тем, связей и файлов.
  При любой ошибке синхронизация останавливается со списком проблем, база не меняется;
- записи из `content/` добавляются или обновляются по `id`;
- записи, которых больше нет в `content/` (или с `"published": false`), **снимаются с публикации**,
  а не удаляются: API их не отдаёт, а избранное пользователей сохраняется и вернётся вместе с ними;
- связи между материалами пересобираются целиком; параллельные запуски сериализуются advisory-lock;
- из `content/fees/*.yaml` загружаются пошлины калькулятора: файлы проверяются (поля, суммы,
  параметры, контрольные примеры) с сообщениями на русском, понятными юристам.

**`npm run db:seed:demo`** — только для разработки и CI: создаёт или сбрасывает демо-пользователя
`anna_kuznetsova` / `anna@example.com` с паролем из `SEED_DEMO_PASSWORD`, тремя избранными
материалами и шестью записями истории. С `NODE_ENV=production` не выполняется. Данные других
пользователей не трогает.

## Команды

| Команда              | Что делает |
| -------------------- | ---------- |
| `npm run dev`        | Запуск из исходников через `ts-node-dev` с автоперезапуском. Типы не проверяются ради скорости |
| `npm run typecheck`  | Проверка типов приложения и тестов без генерации файлов |
| `npm run build`      | Компиляция в `dist/` |
| `npm start`          | Запуск собранного приложения (`node dist/index.js`) |
| `npm run db:migrate` | Сборка и применение новых миграций |
| `npm run db:seed`    | Сборка и синхронизация наполнения из `../content` |
| `npm run db:seed:demo` | Сборка и создание демо-пользователя (не для production) |
| `npm test`           | Сборка тестов в `test-dist/` и запуск API-тестов (`node:test`) |

Тесты работают с реальной БД из `DATABASE_URL`: применяют миграции, синхронизируют наполнение
(демо-пользователя не трогают), поднимают приложение на случайном порту, а созданных пользователей
удаляют в конце. Тесты синхронизации временно публикуют изменённые копии `content/` и после себя
восстанавливают настоящее наполнение.
Если задан `SEED_DEMO_PASSWORD`, дополнительно проверяется вход демо-пользователя.

Продакшен-запуск:

```bash
npm ci
npm run build
NODE_ENV=production node dist/db/migrate.js
NODE_ENV=production node dist/db/seed.js     # наполнение из ../content
NODE_ENV=production npm start
```

Сервер обрабатывает `SIGINT` и `SIGTERM`: перестаёт принимать новые соединения, дожидается
текущих запросов, закрывает пул PostgreSQL и завершается. Если остановка длится дольше 10 с,
процесс завершается принудительно с кодом `1`.

## CI

`.github/workflows/backend.yml` запускается при push и PR с изменениями в `backend/` или `content/`:
поднимает сервис-контейнер `postgres:17`, затем выполняет `npm ci`, `typecheck`, `build`,
`db:migrate`, `db:seed` (дважды — проверка идемпотентности), `db:seed:demo` и `npm test`.
Браузерные тесты фронтенда (`frontend.yml`) тоже поднимают этот бэкенд с PostgreSQL.
Значения `JWT_SECRET`, паролей БД и демо-пользователя в workflow — одноразовые тестовые, не секреты.

### Как добавить новый эндпоинт

1. Описать его и новые коды ошибок в `../docs/api.md`.
2. Запросы к БД — функция в `src/services/<area>.ts`, только с параметрами (`$1`, `$2`, …).
3. Обработчик — в `src/controllers/<area>Controller.ts`: проверка входных данных через
   `src/lib/validation.ts`, вызов сервиса, ответ.
4. Маршрут — в `src/routes/<area>Routes.ts`, подключить в `src/app.ts` **до** `notFound` и `errorHandler`.
   Для защищённых маршрутов — `requireAuth`, id пользователя — `authUserId(req)`.
5. Ошибки для клиента бросать как `throw new HttpError(status, 'CODE', 'Message')`. Express 5 сам передаёт
   исключения из async-обработчиков в `errorHandler`. Прочие ошибки превращаются в `500 INTERNAL_ERROR`
   (или `503`, если недоступна БД) без деталей для клиента.
6. Изменения схемы — новой миграцией, тесты — в `tests/`.

## Технические решения

- **JWT без cookies.** Access-токен (HS256, 15 мин) в заголовке `Authorization`; refresh-токен — случайная
  строка, в БД хранится только её SHA-256-хеш. При каждом обновлении refresh-токен заменяется новым;
  повторное предъявление старого отзывает все сессии пользователя. Logout отзывает refresh-токен.
- **Пароли — scrypt** из `node:crypto` с параметрами OWASP (N=2^17, r=8, p=1), параметры хранятся в
  хеше. Для несуществующего пользователя выполняется такая же проверка, чтобы время ответа не выдавало
  зарегистрированные логины. Цена — около 0,3–0,5 с CPU и 128 МБ памяти на одну проверку пароля.
- **Поиск** — полнотекстовый индекс PostgreSQL (`tsvector` по словарю `russian`, GIN) вместе с
  подстрокой по заранее приведённому к нижнему регистру `search_text`. Словарь находит формы слова и
  слова не подряд; `strpos` сохраняет вхождение внутрь другого слова. Выдача сортируется по `ts_rank`.
- **Миграции — свой небольшой раннер** вместо библиотеки: SQL-файлы, транзакции, advisory-lock.
- **Модули: CommonJS.** `"type": "commonjs"`, `module`/`moduleResolution: NodeNext`. `ts-node-dev`
  не поддерживает ESM. `jose` 6 поставляется только как ESM и подключается через `require(esm)`,
  который поддерживается в Node.js 24.
- **TypeScript 6.x.** TypeScript 7 не предоставляет JS API, на котором работает `ts-node-dev`.
- **`npm audit`.** У dev-зависимости `ts-node-dev` (через `chokidar` → `braces`) есть уязвимость high
  без исправления: DoS при разборе glob-шаблонов. Она касается только локального наблюдения за файлами
  и не попадает в продакшен (`npm audit --omit=dev` → 0 уязвимостей).
