# API бэкенда — документация для фронтенд-разработчика

## 1. Назначение и текущие возможности

Бэкенд веб-приложения на TypeScript + Express + PostgreSQL.

Сейчас это **технический каркас**: бизнес-логика, модель данных и бизнес-эндпоинты ещё не определены.
Что уже работает:

- HTTP-сервер с JSON API;
- проверка работоспособности сервера (`GET /`) и подключения к PostgreSQL (`GET /api/health`);
- CORS для одного заданного origin фронтенда с поддержкой cookies (`credentials`);
- единый JSON-формат ошибок, включая ответ `404` для неизвестных маршрутов.

## 2. Адрес локального сервера

```
http://localhost:3001
```

Порт по умолчанию — `3001`, меняется переменной `PORT` в `backend/.env`.

## 3. Требования

| Компонент  | Версия                                         |
| ---------- | ---------------------------------------------- |
| Node.js    | 24 LTS или новее (поле `engines` в `package.json`) |
| npm        | поставляется с Node.js (проверено на 11.x)     |
| PostgreSQL | любая поддерживаемая версия (14+); нужен только для `GET /api/health` |

Без PostgreSQL сервер запускается, `GET /` работает, а `GET /api/health` отвечает `503`.

## 4. Установка и запуск

Бэкенд находится в папке `backend/` этого репозитория:

```bash
cd backend
npm install
cp .env.example .env   # затем отредактируйте backend/.env
npm run dev            # режим разработки с автоперезапуском
```

Как поставить PostgreSQL и создать локальную БД-заглушку, описано в [backend/README.md](../backend/README.md#локальная-база-данных).

Переменные окружения (`backend/.env`):

| Переменная        | Обязательна | По умолчанию            | Описание |
| ----------------- | ----------- | ----------------------- | -------- |
| `NODE_ENV`        | нет         | `development`           | `development`, `production` или `test` |
| `PORT`            | нет         | `3001`                  | Порт HTTP-сервера |
| `DATABASE_URL`    | **да**      | —                       | Строка подключения: `postgresql://USER:PASSWORD@HOST:PORT/DATABASE` |
| `FRONTEND_ORIGIN` | нет         | `http://localhost:3000` | Origin фронтенда, которому разрешён CORS |

Если переменные заданы некорректно, сервер не запустится и выведет список проблем
(значение `DATABASE_URL` в сообщениях не выводится).

Проверка, что сервер поднялся:

```bash
curl http://localhost:3001/
```

## 5. Существующие эндпоинты

| Метод | Путь          | Назначение                                   | Статусы ответа |
| ----- | ------------- | -------------------------------------------- | -------------- |
| GET   | `/`           | HTTP-сервер работает                         | `200` |
| GET   | `/api/health` | Приложение работает и PostgreSQL доступен    | `200`, `503` |

Любой другой путь или метод → `404` в формате ошибки (см. раздел 8).

Оба эндпоинта технические и не заменяют будущие бизнес-эндпоинты.

## 6. Примеры запросов и ответов

### GET /

```bash
curl -i http://localhost:3001/
```

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "status": "ok",
  "message": "Backend is running"
}
```

### GET /api/health

Выполняет лёгкий запрос к PostgreSQL через пул соединений. Ответ не кэшируется (`Cache-Control: no-store`).

```bash
curl -i http://localhost:3001/api/health
```

База данных доступна:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: no-store

{
  "status": "ok",
  "database": "up"
}
```

База данных недоступна (не запущена, неверные учётные данные, таймаут подключения 5 с):

```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/json; charset=utf-8
Cache-Control: no-store

{
  "error": {
    "code": "DATABASE_UNAVAILABLE",
    "message": "Database is unavailable"
  }
}
```

Причина недоступности клиенту не сообщается — она пишется только в лог сервера.

### Неизвестный маршрут

```bash
curl -i http://localhost:3001/api/unknown
```

```http
HTTP/1.1 404 Not Found
Content-Type: application/json; charset=utf-8

{
  "error": {
    "code": "NOT_FOUND",
    "message": "Resource not found"
  }
}
```

### Пример вызова из браузера

```js
const res = await fetch('http://localhost:3001/api/health', {
  credentials: 'include', // нужно, только если будут использоваться cookies
});
const body = await res.json();
if (!res.ok) {
  console.error(body.error.code, body.error.message);
}
```

## 7. CORS

- Разрешён ровно **один** origin — значение `FRONTEND_ORIGIN` в `backend/.env`
  (по умолчанию `http://localhost:3000`).
- Origin должен совпадать с адресом страницы фронтенда **точно**: схема, хост и порт,
  без пути и без завершающего `/`. Например, `http://localhost:5173` для Vite.
  `http://localhost:3000` и `http://127.0.0.1:3000` — это разные origin.
- Включено `Access-Control-Allow-Credentials: true`: браузер может отправлять cookies,
  если фронтенд вызывает `fetch(..., { credentials: 'include' })` (или `withCredentials: true` в axios).
- Preflight-запросы (`OPTIONS`) обрабатываются автоматически и отвечают `204`.
- Запросы со страниц другого origin браузер заблокирует.
  Инструменты без браузера (curl, Postman) CORS не проверяют.

Если фронтенд работает на другом порту, поменяйте `FRONTEND_ORIGIN` в `backend/.env` и перезапустите сервер.

## 8. Соглашения API

### JSON

- Тела запросов и ответов — JSON в UTF-8.
- Запросы с телом отправляются с заголовком `Content-Type: application/json`.
- Максимальный размер тела запроса — **100 KB**.

### HTTP-статусы

| Статус | Когда используется |
| ------ | ------------------ |
| `200 OK` | Успешный запрос |
| `201 Created` | Ресурс успешно создан |
| `400 Bad Request` | Некорректный запрос (в том числе невалидный JSON в теле) |
| `401 Unauthorized` | Нет действительной аутентификации — когда аутентификация будет реализована |
| `403 Forbidden` | Доступ запрещён — когда будет реализована авторизация |
| `404 Not Found` | Маршрут или ресурс не найден |
| `413 Payload Too Large` | Тело запроса больше 100 KB |
| `500 Internal Server Error` | Внутренняя ошибка сервера |
| `503 Service Unavailable` | Сервис или необходимая зависимость (например, БД) временно недоступны |

Это соглашения для всего будущего API. Сейчас реально возвращаются `200`, `204` (preflight), `400`, `404`, `413`, `500`, `503`.

### Формат ошибок

Любой ответ с ошибкой (статус 4xx/5xx) имеет одну и ту же форму:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Resource not found"
  }
}
```

- `code` — стабильный машиночитаемый код в `UPPER_SNAKE_CASE`. На него можно опираться в логике фронтенда.
- `message` — короткое описание на английском для разработчика. Не предназначено для показа пользователю
  как есть и может меняться.
- Ответы не содержат stack trace, SQL, строк подключения и других внутренних деталей.

Коды ошибок, которые существуют сейчас:

| Код | Статус | Причина |
| --- | ------ | ------- |
| `INVALID_JSON` | 400 | Тело запроса не является валидным JSON |
| `BAD_REQUEST` | 400 | Прочие ошибки разбора запроса |
| `NOT_FOUND` | 404 | Маршрут не найден |
| `PAYLOAD_TOO_LARGE` | 413 | Тело запроса больше 100 KB |
| `INTERNAL_ERROR` | 500 | Непредвиденная ошибка сервера |
| `DATABASE_UNAVAILABLE` | 503 | PostgreSQL недоступен |

Новые коды будут добавляться в эту таблицу вместе с новыми эндпоинтами.

## 9. Пока не реализовано

Перечисленное ниже **не существует** и будет спроектировано отдельно:

- **Бизнес-эндпоинты.** Кроме двух технических эндпоинтов выше, API нет. Пути, форматы запросов и ответов
  будут согласованы по мере проработки страниц и сценариев из Figma.
- **Аутентификация и авторизация.** Нет регистрации, входа, сессий, JWT и ролей.
  Статусы `401`/`403` зарезервированы на будущее.
- **Модель данных.** В PostgreSQL нет таблиц предметной области и миграций.
- Пагинация, фильтрация, версионирование API, загрузка файлов, rate limiting — не определены.

До появления реальных эндпоинтов фронтенд может работать с моками. Формат ошибок и соглашения
из раздела 8 уже действуют и сохранятся.
